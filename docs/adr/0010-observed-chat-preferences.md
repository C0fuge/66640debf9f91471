# ADR 0010: observed whole-chat preference controls

Status: accepted for implementation by root, 2026-11-26, within the owner's resumed development instruction. This approves one optional plugin read method chats.get (API1.1.0, same-major compatibility) and matched setChatFlag/refreshChatFlags app operations. No database migration, new remote product feature, account inventory scan or renderer-selected RPC. App stays34 and the old plugin contract remains the verified baseline until the coherent amendment passes gates. Implement/review contract+SDK changes before the app controls.

## Application operation

Use setChatFlag({thread, flag: "pinned" | "markedUnread", value: boolean}) returning null on an acknowledged plugin success. Require an existing whole-chat row belonging to the persisted account, a valid non-provisional chat ID and null topicId. Reject topic requests before dispatch, even if the parent chat supports flags. Resolve the plugin from the account. Preserve separate platform conversations and accounts, including peers with matching IDs. Only ordinary dialogs are supported by the proposed Telegram adapter. Leave peer-kind validation to that adapter after core ownership validation.

Send exactly one desired boolean in chats.set_flags, mapping markedUnread to marked_unread. Gate on the live chat.flags handshake AND the matching chat.pin or chat.mark_unread parameter capability. Explicit false requires precisely the same gates as true. Absent or null plugin parameters request no change. Reject null app values. Capability true or an object enables its key; false, null and missing disable it. Do not infer capabilities from the displayed flag. Keep muted, archived, pin ordering, message pins, read receipts, counts and topics outside this action.

Acquire the existing whole-thread action lock. Check account enabled, running phase, current plugin handshake and running_account_token for the same owner. Recheck cancellation immediately before dispatch and after response. A replacement run cannot confirm its predecessor. Check host transport binding for restart races before implementation. Pre-dispatch rejection is definite. Once dispatch is possible, cancellation, malformed/lost replies, lost event acknowledgement, ambiguous adapter errors or connection loss must surface safe outcomeUnknown errors. Both transports must classify this operation as a write and never replay it. Audit the generic action_call rejection mapping against the adapter's partial/ambiguous failures.

## Display and reconciliation

The adapter's acknowledged exact-dialog sparse conversations.upsert is the authority. Preserve omitted fields and unrelated chats. An explicit false clears a stored true. Never apply the requested value as a local write. An empty successful plugin reply has no flag payload. Invalidate and reload listChats from committed data. projection.rs currently coalesces nullable flags to false; expose nullable observed values separately or amend the matched app/UI projection before presenting cached false as a confirmed negative. Manual unread is separate from unread_count.

Use sibling keyboard-operable menu and row-selection buttons in ChatListPane. Label the commands “Pin chat”, “Unpin chat”, “Mark as unread” and “Clear unread mark”. For unknown values offer explicit desired actions with an unknown-state label. Disable unsupported or unavailable actions independently. Pending state and unresolved results belong to the exact account/chat/field outside the virtual row. Preserve across filtering, archive tabs, remounts and bridge reconnect. Drop stale async completions after an account generation change. A client restart must not silently convert pending/unknown into a confirmed result; require a fresh observation before enabling further writes.

## Explicit refresh blocker

schemas/methods/chats.json provides account-wide chats.sync with include_archived and a 120-second deadline. It has no chat selector, pagination or inventory bound. The registry has no exact chat-ID dialog read. lookup.username requires a username and can omit the conversation; messages.get/history cannot confirm dialog flags. Empty chats.set_flags has no contract requiring observation. Local listChats, reconnect, timeouts, unrelated sparse events and same-value cached rows cannot clear uncertainty.

## Accepted protocol amendment

Add one optional core-to-plugin method `chats.get` gated independently by `chat.get`. Use the registry default 60-second timeout and no progress or parameter gates. This spelling follows the existing chats namespace and singular chat capability family. A comment on Ingest::apply_conversation already names chats.get, but the frozen registry does not implement it. Under the published §18 versioning policy an additive method warrants **1.1.0**. Retain major version 1, the existing required method set and compatibility with 1.0 peers. Capability presence governs dispatch. Coordinate version constants and golden expectations; do not silently edit the meaning of frozen 1.0.0.

* In schemas/methods/chats.json define chats.get.params as a reference to common.json#/$defs/ChatParams (exactly the two documented inputs account_id and chat_id, extensible per §18). Define chats.get.result as an extensible object requiring one non-null conversation referencing ../dto/conversation.json#/$defs/Conversation. ID and kind are required by that DTO. Missing or null optional flags express lack of a fresh observation. Return NOT_FOUND for a definitively absent ordinary chat, established transport/auth errors otherwise. A failed, missing or mismatched read never deletes a row. lookup.username's result permits absent conversation and targets a username; Empty, arrays and optional-message wrappers cannot represent the required success. Do not overload include_archived, send an undocumented selector to sync, or broaden the setter.
* Register the method in schemas/methods/registry.json and key in schemas/capabilities.json. Amend plugin API §§10.1, 11.15, capability table and version history; retain setter input and Empty result. Clarify §10.1 specifically for this app flow: an accepted preference write with an Empty result is no source of observed flags. Use an acknowledged observed upsert or a fresh targeted read as evidence. Handle old plugins which emit no event by offering refresh. A read's returned DTO is the observation, requiring no second event and never emitting conversations.synced.
* Update Rust ch-protocol typed alias ChatsGetParams = ChatParams, ChatsGetResult wrapping Conversation, registry/capability metadata, API version, and corresponding Python SDK types, registry, capabilities and version. Check Rust ch-plugin-sdk handler registration and typed dispatch through its existing protocol exports; extend SDK fixtures and conformance in both languages. Keep Rust/Python on the same schema truth. Test mixed 1.0/1.1 peers both ways, with unsupported handler/cap absent and supported dispatch present; inventory without a live handshake disables controls.
* In Telegram reuse the exact-dialog read helper with one resolved marked peer, same account/run and per-account sync lock. One GetPeerDialogs request for that peer, no inventory traversal or writes. Validate raw dialog and entity identity/kind. Return only id, kind and observed pinned/marked_unread. Both TL bits decode to booleans on an ordinary Dialog. Keep uncertain/unsupported peer forms from masquerading as false. No additional platform feature is implied.
* In App add refreshChatFlags({thread}) returning {pinned: boolean|null, markedUnread: boolean|null}. Require whole-chat scope and chat.get, independently of write caps. Reuse existing owner/run and action-lock checks before reading and before committing; validate response id and kind against the stored target. Use existing Ingest::apply_conversation(plugin_id, account_id, sparseConversation) and publish its committed Applied changes through the bus. Restrict this app consumer's projection to id/kind and observed flags, preserving unrelated fields and guarding stale account lifecycle. Apply only to the still-existing owner/row, avoiding resurrection if removal races the read (an atomic existing-row guard may be needed). Return field values from the validated response after commit, never from the merged row: retained older true alongside an omitted fresh flag must yield null. Concurrent external events may supersede the observation; it is a point-in-time read. No schema migration, generic RPC or raw client.
* Expose nullable flags on the matched app/UI ChatRow projection (DB already uses Option<bool>). Positive decorations still test for true. An explicit refresh clears uncertainty only for the exact target/field observed in a matching current context. To survive remount/restart without persisting uncertainty, require a new explicit refresh on every newly opened action panel before permitting writes, consume the fresh observation when submitting, and require another explicit review before another attempt. Reconnect/run replacement invalidates it. Gate UI writes on availability of both the read and field-specific write capability. A read failure leaves uncertainty visible and never replays a setter.

## Accepted application read proof refinement

A chat/account ID can survive removal and recreation. A renderer-only refresh
marker cannot establish which account run produced the observation. Match the
existing reaction-context pattern: refreshChatFlags returns {thread, sessionId,
contextToken, pinned, markedUnread}, with required nullable flag values and a
nullable token. setChatFlag additionally requires sessionId/contextToken. A
short-lived one-use server proof binds the exact persisted owner, whole-chat
row, plugin handshake and running-account token to the actually observed fields.
Unknown fields cannot authorize writes. Bound contexts to64, lifetime60seconds,
and owned read/write tasks to4; refuse excess work without an unbounded queue.
Consume a proof before dispatch, reject old generations and stale replies, and
never manufacture confirmation from cached row flags. Reuse existing capability,
lease and transport mechanisms; no database table or generic command interface.
UI panels require explicit refresh, consume their observation on an attempt and
keep ambiguous attempts unresolved until a fresh exact observation. No automatic
read or write follows panel open, account switch or reconnect.
