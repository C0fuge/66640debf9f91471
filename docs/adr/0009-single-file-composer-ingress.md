# ADR 0009: single-file composer ingress

Status: accepted for implementation by root, 2026-11-26, within the owner's continued development instruction. Baseline: verified main b422a78/checkpoint b515958, public dc808f3/Verify45794077036. Application API remains30 until all four new operations and their UI pass integrated verification. This ADR approves additive core admission/upload-directory helpers and one direct already-locked digest dependency; no database migration, plugin wire/SDK change, generic renderer filesystem access or real-account action.

## Decision and user experience

An explicit Choose file action opens one native chooser. Rust stages one bounded private copy for the exact account, platform plugin, chat and topic. The composer displays its sanitized name, length and a signature hint. A separate Send action admits that copy to the existing outbox with a literal caption and optional send-as-file and spoiler flags. Local admission, transfer progress and confirmed delivery are distinct facts.

The slice covers Linux native open, local staging, admission, scoped recovery and cancellation. Album, recording, voice/video notes, paste/drop, preview, reply selection, scheduling, remote sources and poll creation are separate work. A browser without an injected synthetic fixture can read receipts but cannot choose a file. Renderer code receives neither filesystem permissions nor an attachment URL.

## Four application operations

Add required `Inventory.composerAccess.chooseFile: boolean` for provider availability. The live account and thread determine which actions are currently eligible. Keep ADR0007's media session and ADR0008's reaction context separate. After all three ADR0008 operations, the four additions take the application API from 30 to 34 operations.

```ts
type IngressState =
  | "choosing" | "copying" | "ready" | "verifying" | "enqueuing"
  | "enqueued" | "admissionUnknown" | "cancelling" | "cancelled" | "failed";

type IngressReason =
  | "unavailable" | "chooserUncertain" | "unsafeSource" | "sourceChanged"
  | "stageChanged" | "tooLarge" | "capacity" | "targetChanged"
  | "interrupted" | "storage" | "admissionUnknown" | "integrity";
interface FileStage {
  stageId: string;
  sessionId: string;                  // current ingress service session
  requestKey: string | null;          // null for a stage imported at startup
  thread: ThreadKey;                  // exact accountId/chatId/topicId
  state: IngressState;
  name: string | null;
  bytes: string | null;               // canonical unsigned decimal strings
  format: "jpeg" | "png" | "other" | null;
  copiedBytes: string | null;         // local copy only
  outboxId: string | null;            // local client ID, available from claim
  outboxRow: "present" | "missing" | "unchecked" | null;
  error: { code: CoreFailure["code"]; reason: IngressReason;
    outcomeUnknown: boolean } | null;
}
interface FileStagePage {
  sessionId: string;
  items: FileStage[];
  nextCursor: string | null;
  remainingRequestKeys: number;
}
startFileSelection(p: { thread: ThreadKey; sessionId: string;
  requestKey: string }): Promise<FileStage>;
listFileStages(p: { thread: ThreadKey; requestKey: string | null;
  cursor: string | null }): Promise<FileStagePage>;
cancelFileSelection(p: { thread: ThreadKey; sessionId: string;
  stageId: string }): Promise<FileStage>;
enqueueFile(p: { thread: ThreadKey; sessionId: string; stageId: string;
  caption: string; asFile: boolean; spoiler: boolean }): Promise<FileStage>;
```

All commands reject unknown fields. Existing opaque thread identifiers keep the 1–256 UTF-8 byte protocol limit. Use independent random 128-bit lowercase hex stage, session and local client IDs, and 1–64 ASCII alphanumeric, hyphen or underscore selection keys. Exact owner/thread scope applies to every lookup, including whole-chat view when its topic is null. Receipt reads and cancellations need the persisted matching owner and receipt, even if posting has since become unavailable. Missing/foreign IDs give the same scoped error. A stale session cannot mutate even a surviving stage.

Start atomically reserves the job and binds the key before invoking the chooser. The process ledger holds every accepted start, including failures and cancellations, up to 4096 keys globally. Same key and exact scope recovers its snapshot, even when new work is full. A different scope conflicts or returns a scoped missing result without exposing the original. No TTL eviction or silent rotation. New admissions at capacity fail before accepting the key. A lost start is recovered by exact-key list in the same session. An old session cannot be refreshed into a new start by the client.

List permits either a key or a cursor, or neither. A key returns zero or one current-process receipt, with no continuation. Otherwise page newest creation first with an opaque session/exact-thread cursor bound to a stable creation ordinal. Loaded persistent stages receive deterministic ordinals before fresh starts, and carry null request keys. Attach at most 16 stage snapshots and enforce at most 128 KiB serialized per new operation result, including maximal escaped IDs. End a page early with a continuation if necessary. Revalidate session and consume results only in the matching active panel. Account invalidation triggers bounded reads. It never initiates a native operation.

Each mutation returns a short local snapshot. In particular, `enqueueFile` returns **FileStage**. A 2 GiB rehash can exceed the existing 30-second app request window. Return `verifying` or a later observed state after reserving an owned task. List follows that task through `enqueuing` to its observed outcome. This avoids manufacturing an OutboxItem, echo or delivery state when no row is visible. Native open, hashing, copying and storage settlement continue under owned leases if the caller disconnects. Classify all three mutations as side effects in both transports. On lost replies recover locally, without replay. Keep the text draft separate and preserve it after ambiguous replies.

## Scope, capabilities and projection

Resolve the persisted account row, owner plugin, enabled/running account, live handshake and exact non-gone conversation/topic. Reject a closed topic or explicit `can_post=false`, following the existing composer rule for unspecified permissions. Recheck before opening the chooser, publishing ready and immediately before admission. Capture account creation identity and process lifecycle generation. Reject foreign owners, disabled/replaced accounts and stale callbacks. Never derive an account from contact/person grouping. A topic-null stage cannot be transferred to a topic or vice versa.

Read raw `send.file`. Missing/false disables it. True or an object lacking `max_bytes` uses 2,147,483,648. A present limit must be a positive integral JSON value representable under the decoder's unsigned integer rules. Reject null, fractions, strings, zero, negative/invalid declarations. Enforce the smaller of that limit and 2 GiB at open, copy and enqueue. Newer unrecognized object fields are ignored. Gate `asFile=true` and `spoiler=true` on live `send.as_file` and `send.spoiler`. Set only requested true fields in plugin params. Explicit false counts as present in the frozen gating rules. UI availability is a hint, backend checks are authoritative.

Caption is literal, bounded by 1024 Unicode scalar values and 4096 UTF-8 bytes, including whitespace as entered. Omit an empty caption, leave entities absent, preserve all other caption bytes without normalization. Rust constructs one `MessagesSendFileParams` using the exact thread, managed path and sanitized filename. Inspect only the bounded prefix of the staged bytes. JPEG FF D8 FF and PNG's eight-byte signature project as such. Other bytes project as other. Use document kind for forced-file or other, photo for recognized images otherwise, giving core's local echo a determinate kind. A signature identifies a header, never verifies an image. Omit MIME, sizes/dimensions unsupported by params, execution/preview data and unrelated optional fields.

Extend existing OutboxItem projection with required `kind: "sendText" | "sendFile"`, `doneBytes: string|null` and `totalBytes: string|null` in both clients. Use only nonnegative core upload observations, preserve unknowns and drop inconsistent totals. Never count local copy/verification as upload. Coalesce progress-only stage/file invalidations to at most 4 Hz/account, retaining terminal/state notifications promptly. Existing listOutbox includes text and file and preserves whole-chat aggregation or selected-topic filtering. Each item carries its exact thread. Existing cancelOutbox accepts a file only for its exact owner/thread and forwards core cancellation semantics. Sending may still settle sent, and an unresolved outcome stays unresolved. Existing retryOutbox rejects **every** file, including failed files, even if invoked directly. Preserve existing text retry and core policy for safe pre-dispatch waits/backoff, authentication and flood waits. UI shows the outbox independently of the stage, including outcomeUnknown, without a file retry control.

## Native selection and source authority

Keep public Rust `SaveDialog`, its callback and `App::set_save_dialog` signatures. Add a separate setup-only `OpenFileDialog::choose_open(callback)` and `App::set_open_file_dialog`. The callback may reuse the existing Rust result shape. In native setup coerce the same Arc of one provider into both traits. The provider owns one reservation across Open and Save. Reuse the pinned zbus 4.4.0/url 2.5.9 transport, worker model, known-owner resolution/activation, subscribe-before-call, response sender/path/interface/member verification, random expected handle and strict singleton local file URI handling. Use FileChooser.OpenFile with fixed single regular file options (multiple=false, directory=false), a fixed title, and empty parent as in the current native integration. Keep parent/modality semantics honest. No renderer options, fallback process, JS dependency, Tauri permission or native dependency change.

Response 1 is a settled cancellation, 2 a settled failure and a verified singleton success enters Rust-only source validation. Pre-dispatch unavailability may release the reservation. Missing/wrong handle, transport loss after request dispatch or unproven settlement latches it as in Save. Logical cancellation/shutdown invalidates callbacks without freeing a possibly live chooser. A late selection after revocation is dropped. A chooser-only uncertainty maps to failed/chooserUncertain. No file admission or remote delivery occurred. Distinguish this from admissionUnknown. The source guarantee begins when a validated descriptor is held. A chooser URI provides no proof of the inode visible at click time.

Open only a strict absolute local path. Reject traversal, NUL, ambiguous encoded separators or dot components before URL normalization can erase them. Use held no-follow ancestry, final no-follow/nonblocking/CLOEXEC read-only descriptor, regular nonempty single-link file and bounded path depth. Reject symlink components, FIFO/device/socket, private application data including accounts/state/sessions/cache/uploads/DB/logs, any additional private roots already supplied by the running core configuration, and sources for which the boundary cannot be established. Compare held directory identities as well as lexical ancestry. For the initial Linux boundary, disallow untrusted mount aliases/document exports when they obscure the original tree. Keep mount inspection bounded to at most2MiB/8192 records and path depth64; recognize ordinary filesystem roots and proven Btrfs subvolume roots without guessing that every non-slash root is a bind mount. Reject an unverifiable source rather than changing mount state or requesting privileges. Concretely, reject virtual/exported sources with unverifiable backing and compare mount IDs for every held component, including the final file. Accept a mount crossing only when its boundary is a verified ordinary filesystem root in the trusted local mount table. Reject subtree/file bind aliases and ambiguous same-device aliases of a private mount. Keep these checks inside the Linux opener. Test a bind-mounted descendant or equivalent synthetic identity fixture. This check neither reads legacy application data nor scans the home directory.

Keep the source fd and validated directory chain through copying. Check named entry identity against the held fd, current ancestry and dev/inode/mode/owner/nlink/size/mtime/ctime before, during bounded copying, and at publication. Copy from that fd only. A source change/replacement invalidates the copy. Derive a display basename only, dropping controls (including bidirectional controls), invalid components and path separators, with a bounded generic fallback and a 255 UTF-8 byte maximum at a character boundary. URI, original path, fingerprints, hashes and local staging paths never enter the renderer, diagnostics or logs. Source ownership metadata is a fingerprint, not a requirement that an explicitly chosen readable regular file be owned by this UID; do not copy cache-only UID authority rules into the generic source opener. Only the private manifest holds staged identity and digest, never the original path. The frozen generic upload contract still accepts readable absolute user paths from other core callers. Telegram continues to hold/recheck its input as implemented. App-only staged authority and private file modes confer no OS sandbox, no universal restriction on plugin path reads, and no protection against an adversarial process running as the same user.

## Managed storage and finite ownership

Introduce `HostConfig::upload_dir(account_id)` as the account's new uploads sibling of state/cache, using the existing host account directory helper. Keep AccountStartParams and plugin/SDK contracts unchanged. Only the current persisted owner may allocate here. Validate root identity, permissions and collision-free account mapping; two distinct persisted account IDs mapping to the same sanitized directory block ingress for that root. The helper selects a directory convention, never an existing authority field. Use the running app's existing data-dir lock for one writer per store.

Under a verified account root use one owner-only stage directory per backend-generated stage ID. Generate the fixed independent client ID before publication. Use fixed managed child names such as `bytes` and `manifest.json` inside this random directory; no filename, raw owner ID, path, caption or user input is interpolated into child names. Open via held directory descriptors, single-component exact names, no links. Directories 0700, transient files 0600. Stream in 64 KiB chunks, enforce length and cancellation, compute SHA-256; flush and sync the private byte inode, publish its exact identity without clobber, apply read-only 0400, sync the inode again after its metadata changes, close writable fds and sync the binding. Take final staged fingerprint after link/mode changes. Ready becomes visible only after its manifest and requisite parent directories are durably synced, including newly created directories. An interrupted copy never becomes ready. Use existing libc file primitives and a direct ch-app edge pinned to the already locked `sha2 = "=0.10.9"` (Cargo.lock also contains 0.11.1). No new resolved packages or chooser dependencies. Use the crate's streaming SHA-256, with lock graph verified in CI.

Version-1 JSON manifests use strict typed decoding, reject unknown/duplicate fields, invalid variants, IDs, corrupt lengths/digest/fingerprints and files over 64 KiB. Store version, stage ID and fixed client ID, exact bound account/plugin/account creation identity/thread, creation time, sanitized name, size, signature hint, staged fingerprint and SHA-256. The durable phase is one of ready, claimed, consumed or discarded. Claimed/consumed additionally require the exact canonical caption and booleans. Keep the managed path deterministic from verified directory bindings. Never trust a manifest-supplied path. Canonical comparisons use actual typed fields, not a digest instead of equality. Use no-clobber initial publication and same-directory temporary+fsync+atomic replacement+directory fsync under the stage lease for transitions. A sync error after rename can be ambiguous. Freeze that stage and reconcile; never call core when claim durability is in doubt.

Hold at most 16 **byte-bearing** stages globally (including claimed, consumed and incomplete allocations), 8 GiB globally and 4 GiB/account. Charge logical file length, including sparse files, before allocating/copying. Reserve job capacity before opening a chooser. Reserve retained-stage slot and size atomically before copying, or return capacity with no ready file. Count reservations and retained actual bytes once, never twice or optimistically freed. One concurrent byte-copy or full verification scan globally, four owned ingress jobs (including chooser, waiting, verification and admission). No unbounded task queue. At quota reject new work while allowing list, cancel, recovery and sends from already charged ready stages. A managed volume can run out of actual disk space below these application limits. Reserve/settle errors leave accounting conservative.

Process receipts cover choosing/copying/cancelled/failed jobs and their request keys, including discarded ready stages, for this process only. Persisting a ready/claimed/consumed stage is the separate restart boundary. A process restart creates a fresh session. An interrupted chooser or partial copy has no renewable authority, no automatic reopen and no ready stage. If a recognisable interrupted record is surfaced, report failed/interrupted; otherwise the old process receipt simply ends. Recover existing ready stages under the new session only after owner and manifest validation. Every send still requires a fresh explicit action. A missing stage ID never creates a stage or core row.

Startup inventories anchored account/upload roots, including orphan managers left by failed removals, before granting new ingress reservations. Keep the scan finite, e.g. at most 4096 account-directory entries and 256 managed entries across roots per inventory, fixed grammar/depth, bounded manifest reads and no link following. Stop on either ceiling and disable new allocations until trustworthy accounting is possible. Count orphan/incomplete/excess entries and lengths conservatively; corrupt or unaccountable storage blocks new writes where aggregate bounds cannot be proven. Leave it in place. Do not walk arbitrary subtrees, auto-repair corrupt claims or erase evidence. Unrelated app functions remain available. List metadata reads do not hash multi-GiB files. Reopen and verify a recovered ready file under a bounded worker before first use.

A single stage lease serializes copy, verify, ready discard and claim. Verify the staged owner/directory/name, exact held regular file, immutable metadata and SHA-256 against the manifest on every **initial admission**, including after restart. Recheck binding/fingerprint and metadata while reading, at end and immediately before core. Only the verified copy may become a plugin request source. Keep the read-only stage after admission. The async worker opens the path later under the pre-existing generic protocol. This proposal provides local integrity at admission, constrained application writers and conservative retention. It does not retrofit later cryptographic validation into every generic plugin dispatch. After an ambiguous commit, never “repair” a staged file or substitute another file under that path.

Explicit ready discard (or an optional 24-hour idle sweep with identical proofs) must win the same stage lease before any claim/verification task. Default to explicit discard in this slice. Require a durable ready phase, intact binding, no active read/copy/claim lease, absence of its fixed outbox row, and evidence that the private unpublished path has never been handed to a worker/echo. Foreign, corrupt, legacy or otherwise unprovable references keep their bytes and charge. If alternate stored references cannot be excluded under the store's ownership invariant, use a bounded reference check and retain on exhaustion or ambiguity. Persist discarded before unlinking, unlink only verified managed entries, sync and settle; release quota only after verified removal. A crash after the discard mark cannot resurrect ready. Preserve the session key receipt. Keep **all claimed, consumed and admission-unknown bytes** across success, failure, cancel, row deletion and restart. Local echo media may still refer to them. Failed is insufficient proof of worker quiescence. The product ceiling is real: 16 consumed stages or either byte budget can block further selections indefinitely. Display a capacity message explaining retained sent files. Future reference-safe reclamation is separate.

Explicit account removal already recursively removes that account's directory and cascades DB rows. Serialize ingress teardown with removal: close owner admission, revoke chooser generations, and cancel/settle any task that can publish, claim or touch the account root. Do not await an unresolved native dialog on the lifecycle/UI thread. Its late callback lacks access to storage. Never recreate a removed root from a late worker. Charge leftovers if filesystem removal fails. Do not expose old stages to a replacement account. Account removal is a pre-existing explicit lifecycle action, not a general-purpose upload cleaner.

## Admission protocol and recovery

1. Start from a validated ready stage under the current owner/session. Obtain the same-stage lease and one owned job. Freeze the proposed exact caption and booleans in the in-process verification task before returning its receipt. An identical concurrent request sees that receipt. A different intent conflicts. On a definite preclaim eligibility/capacity failure the stage can remain ready with a bounded error. Damaged staged bytes fail closed and are never offered for send. Cancellation may win until the durable claim hand-off begins. A cancellation request that wins latches no-admission; if a syscall is pending show cancelling until it settles.
2. After full hash and live target/option checks, atomically and durably replace ready with **claimed** including canonical intent, fixed ID and immutable staging identity. The one owned task that completed *this* live ready-to-claimed transition alone gets authority to call core once. Enqueuing spans claim persistence and the outstanding local call. Ambiguous claim persistence yields recovery only, with no core call. Never reconstruct that initial authority from a later manifest read or a missing DB row. Once the hand-off wins, stage cancellation returns conflict or the current claimed receipt; a retained outbox row may be cancelled through cancelOutbox.
3. Add one narrowly scoped core entry point, e.g. `enqueue_with_id(expected_owner, client_id, request, sender)`. Keep existing random `enqueue(account_id, request, sender)` and caller behavior. Use existing globally unique outbox.client_id and one write transaction under ingest. Check current account ownership in that transaction. Compare raw retained row's account, chat, exact nullable topic, kind, method and full canonical typed wire params with identical omission/presence rules; compare parsed structures, not JSON key ordering. Owner includes the expected plugin and persisted account identity supplied by the app. For a matching duplicate return the retained row in any state, without worker restart/wake, echo creation, counters, notification or new send. A mismatch conflicts without disclosing the foreign row.
4. Look up the row **before any echo mutation** in that same transaction. `apply_local_echo_with` currently creates an echo before its callback; doing the duplicate check only inside its callback could recreate an echo after the original was adopted. Factor the existing echo mutation into the transaction as needed. For a fresh ID, insert the echo and typed request atomically, then emit existing postcommit changes/start scheduling once. A concurrent unique collision must settle by rolling back any speculative work and comparing the winning committed row, without duplicate events. A postcommit notification/worker error is not proof of failed admission. The core seam guarantees idempotent admission only while the row is retained. No DB tombstone or migration.
5. Return a confirmed exact row to the owner task and persist **consumed**. A lost reply, postcommit error, crash or failed receipt sync leaves the claim recoverable by exact value comparison, never by an insertion. Core's `get_by_client_id` returns an OutboxItem without params; reconciliation must inspect the raw retained row, e.g. a narrow read-only matching helper sharing the canonical comparator with admission and using the existing DB query. A changed/corrupt owner, path or payload cannot establish success. Separate integrity conflict from an absent row. Use an existing matched ID for all subsequent views. No file client ID is passed to Telegram.

| Durable/observed evidence | App receipt | Allowed action |
|---|---|---|
| Valid ready, no durable claim, verified owner | ready, outboxId null | explicit review/send or discard |
| Same live owned claim task is still executing | enqueuing, fixed ID once claimed | observe, never launch a second task |
| Claimed, exact matching row | enqueued, present after reconciliation | observe delivery and use existing eligible cancel |
| Recovered claimed, row missing | admissionUnknown, fixed ID, missing, outcomeUnknown=true | read-only recovery forever on absence |
| Claimed, lookup unavailable or integrity mismatch | admissionUnknown, unchecked, bounded storage/integrity reason | recover only, never return the mismatched row |
| Consumed, matching row | enqueued, present | observe/cancel retained outbox item as eligible |
| Consumed, row missing | enqueued, missing, no assertion about delivery | show “Added to outbox. Delivery record unavailable.” |
| Consumed, lookup unavailable or mismatched | enqueued, unchecked, storage/integrity reason | preserve known local admission, suppress foreign/misleading delivery info |
| No stage after discard/removal/deletion | same-process retained terminal receipt if authorized, otherwise scoped missing | no reconstruction, no admission |

An enqueued state means proven local admission. A failed/outcome_unknown delivery from core remains a separate row state. A claimed stage without a row can result from a crash just before insert or deletion just after insert. Absence never resolves that ambiguity. If a matching row later becomes visible, read-only reconciliation may prove admission. A ready manifest unexpectedly accompanied by its ID in the outbox is an integrity conflict: freeze it, never invoke the insertion seam. Changed caption/options after claim conflict even if the row was removed. After both manifest and row disappear, commands targeting that stage can only return retained process evidence or scoped missing. Do not search by filename/content, infer an admission from an unrelated echo, generate a substitute ID, recreate a stage from its ID or auto-reselect a file. A knowingly fresh selection with a fresh key is a new user intent, not a retry button for unknown delivery.

Implement and verify complete library boundaries first: core admission, private file/store helpers and additive native OpenFile support. These helpers do not advertise a composer feature or enable controls. Only then integrate the scoped ingress service and matching four-operation UI; do not merge an unverified user flow. Preserve the existing Save API and its tests.

The expected row contributes account ID, plugin ID and creation identity only; labels/settings are not intent identity. Canonical typed request parameters supply the rest. Use a fixed, non-disclosing `OutboxError::AdmissionConflict` for a foreign/different retained intent. Invalid client IDs remain InvalidRequest. ## Accepted removal interlock refinement

Source review of `Accounts::add/remove` found that a post-delete notification
cannot protect file writers: creation did not share removal's lifecycle lock,
IDs can share one sanitized account directory, and cancellation of an awaiting
future does not stop its blocking filesystem/SQLite work. The app integration
must address these concrete races before enabling file ingress.

Add the narrow `Accounts::storage_lease(&AccountRow)` async accessor returning
`Result<(CancellationToken, OwnedRwLockReadGuard<()>)>` from existing Tokio
primitives. Validate the exact persisted owner, acquire the storage-directory
read lease, then recheck identity and closing/revocation under that lease. The
chooser keeps only the revocation token; it reacquires a fresh lease and checks
the original token before touching storage. Removal cancels the exact owner
before waiting for the directory write lease, and holds it through teardown.
Distinct owners sharing the same sanitized directory cannot bypass that drain;
ingress rejects collisions, and removal must not recursively erase a root still
owned by another persisted account.

Serialize account creation and destructive removal through their actual
completion, including secret rollback and account-ID reuse. Preserve lifecycle
mutex identity for existing waiters. An owned operation retains gates when its
caller drops the future; a detached blocking syscall may not outlive its gate.
Wrap the existing multi-statement account deletion in one transaction with an
exact owner recheck. Restore a fresh generation only after proven rollback and
unchanged persisted ownership; ambiguous teardown remains closed. No DB schema,
plugin wire, renderer removal command or generic hook framework is added.
